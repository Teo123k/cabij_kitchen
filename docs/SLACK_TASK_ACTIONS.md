# Local Slack task actions

The existing text handoff is unchanged by default. The optional interactive handoff adds complete and reopen buttons to a filtered view of at most 20 tasks. Each button references an approved package, project revision and task; it does not carry an actor chosen by the sender.

The local bridge accepts Slack-signed form payloads at `/api/local-slack/actions`, verifies the HMAC over the raw bytes and a five-minute timestamp, checks the expected workspace, and calls a server-only database function. The function resolves an administrator-provisioned Slack team/user binding to a current kitchen member, deduplicates action timestamps and uses the existing task-completion guard for current trusted packages, membership, task identity and sample rejection. Anonymous and ordinary authenticated users cannot invoke that function or edit bindings. Duplicate requests are harmless. The signing secret and service key stay server-side.

Local configuration requires `CABIJ_SLACK_SIGNING_SECRET`, `CABIJ_SLACK_TEAM_ID`, `CABIJ_CALCULATION_SUPABASE_URL` (loopback only) and `CABIJ_CALCULATION_WORKER_KEY`, as well as a Slack app with interactivity enabled. An administrator must provision verified team/user-to-kitchen-member bindings in `slack_kitchen_members_v1`; these bindings are sensitive authorization decisions and are not created from a Slack message or self-asserted browser input. Remove the binding if access is revoked. The local bridge only accepts loopback connections and a localhost Host header: a separately managed HTTPS reverse proxy that forwards to loopback with that Host would be required for Slack to reach it. No proxy or Slack app was configured here.

The schema migrations have been applied to the active `cabij_os` Supabase project, but it contains zero Slack identity bindings. The dashboard now exposes owner/manager-only binding management; no binding is created automatically. No live Slack message or callback was tested. Production still needs a secure proxy/deployment, staging end-to-end tests, durable delivery journal, concurrency and recovery testing, and a response strategy that meets Slack's three-second acknowledgement requirement. The dashboard currently needs manual completion refresh; a button updates stored state but does not automatically notify the team or rewrite the original Slack message.
